## 设计决策（基于限流实测 + 架构复用分析）

### 决策 D1: REST 全市场轮询（而非全量 WS 订阅）

**fapi `/fapi/v1/klines` 限流（已实测，来源 Binance Open Platform 文档 2026-06-19）:**
- weight 分档（按 limit 参数）: `[1,100)=1`、`[100,500)=2`、`[500,1000]=5`、`>1000=10`
- IP 级 weight 上限: 2400/分钟（USDⓈ-M Futures）

**扫描预算测算:**
- 标的池 ~400 USDT 永续 × 4 TF = 1600 请求/轮
- 用 `limit=99`（weight=1，最省），单轮总 weight = 1600
- 占每分钟上限 67% → 单轮耗时按「错峰分批」分散在 ≥45s 内，**轮询间隔默认 60s**（保留 33% 余量给其他 fapi 调用如 exchangeInfo/fundingInfo）
- 99 根 K 线满足检测器最小窗口需求（`atrPeriod(14)+dropMaxCandles(3)+recoveryMaxCandles(2)+swingLookback(~5)+2 ≈ 26` 根），余量充足

**为何不用全量 WS（1600 stream）?**
- ROADMAP Phase 3 gating question #4 与 REQUIREMENTS Out-of-Scope 表均明确排除「全市场 ~400 标的默认开启 WS」（移动端承载有限）
- UAT gap 用户决策明确要求 REST 轮询 + 命中精跟，而非全量 WS

### 决策 D2: 错峰分批并发（避免瞬时 weight 尖峰）

- 每批 8 并发（`Future.wait` 批内并发，批间等待 200ms）→ 1600 请求 / 8 ≈ 200 批，单轮约 40-50s 完成
- 批大小 8 在 IP 级 2400/min 限流下安全（瞬时 8 weight × 多批错峰，远低于瞬时上限）
- 单请求 30s timeout（沿用 `BinanceApiService.getRecentKlines`），失败计入下一轮重试，不阻塞当前轮

### 决策 D3: 命中精跟生命周期（避免精跟集合无限膨胀）

- **加入**: scanner 命中反弹（detector 返回非 null signal）→ `alertService.trackSymbols({symbol})` → 该 symbol warm-up + 增量 WS 订阅（`streamService.subscribe`，per D7）
- **维持**: 精跟中每根收盘 K 线走现有 `handleClosedKline` 流水线，更新 Provider
- **退出**: 连续 `N` 根收盘未刷新出反弹信号（默认 N=3）→ `untrackSymbol` → `streamService.unsubscribe` 取消该 symbol 订阅 + 移除 Provider 信号
- **上限（FIFO 驱逐，per B2）**: 精跟集合硬上限 30（防止 WS 连接数膨胀，移动端友好）；超限时按 **加入时间最早（FIFO）** 驱逐，即 `untrackSymbol(_trackedSymbols.first)`。FIFO 比按评分驱逐更简单可测（无需 per-symbol 评分 Map），且足够避免连接膨胀——评分在 Provider 层已展示，UI 仍按评分排序。

### 决策 D7: 增量 WS subscribe/unsubscribe（B1 拍板：方案 A）

**现状**: `ReboundKlineStreamService.connect` 全量重建连接；`_ShardConnection.streams` 是扁平 `List<String>`，无 stream→connection 索引，无法实时增量取消订阅。

**拍板: 方案 A（增量订阅，推荐）**，原因: disconnect+reconnect 会触发所有精跟标的重新 warm-up，造成精跟命中标的的信号真空，与「命中自动进入精跟」语义自相矛盾。

**具体子步骤（task2 内完成）:**
1. 在 `ReboundKlineStreamService` 新增 `Map<String, _ShardConnection> _streamToConn = {}` 索引（streamName 形如 `btcusdt@kline_15m` → 持有该 stream 的 connection）。
2. `connect` 内 `_openConnection` 成功后填充该索引（每个 stream 对应其 conn）。
3. 新增 `Future<void> subscribe(List<String> addSymbols)`: 若尚未 `isConnected` 则按现有 `connect` 全量启动；否则对每个 addSymbol × 每个 `_subscribedTimeframes` 生成 streamName，选容量未满（streams.length < maxStreamsPerConnection）的 connection，通过 `conn.channel!.sink.add(jsonEncode({'method':'SUBSCRIBE','params':[...],'id':...}))` 发实时 SUBSCRIBE（复用 `_openConnection` L137-145 的消息格式），并更新 `conn.streams` + `_streamToConn` + `_subscribedSymbols` + 触发 `warmUp(addSymbol, _subscribedTimeframes)`。
4. 新增 `void unsubscribe(List<String> removeSymbols)`: 对每个 removeSymbol × timeframes 生成 streamName，查 `_streamToConn` 取其 connection，发 `{'method':'UNSUBSCRIBE','params':[...],'id':...}`，从 `conn.streams` 与索引移除，从 `_subscribedSymbols` 移除，清理 `_buffers[removeSymbol]`/`_warmingUp`。
5. 单测（task2 verify 一并跑 `rebound_kline_stream_service_test.dart`）: 注入 mock channel 断言 subscribe 发出含新增 stream 的 SUBSCRIBE JSON、unsubscribe 发出对应 UNSUBSCRIBE JSON、`_streamToConn` 索引正确更新。

### 决策 D4: 编排器接入扫描器（最小侵入）

- `ReboundAlertService` 新增 `attachScanner(scanner)` + `trackSymbols(Set)/untrackSymbol(String)`
- scanner 通过回调 `onHits(Set<String> hits)` 通知编排器（不反向依赖，避免循环）
- 编排器内部仍持有 `ReboundKlineStreamService`，精跟通过现有 `connect`/`warmUp` 接口扩展订阅集合
- `start()` 改为接受**空**初始列表（无全量订阅），改由 scanner 驱动精跟集合

### 决策 D5: UI 数据源切换（保留现有 UI 组件）

- 删除 `_defaultSymbols` 硬编码与 `sublist(0,50)` 截断
- initState 创建 scanner + alertService，调用 `alertService.start([])`（空初始）+ `scanner.start()` 驱动
- 新增扫描状态横幅（在 warm-up 横幅之上或并列）：「全市场扫描 · 第 N 轮 · 精跟 M 个」
- 信号列表/sparkline/死猫/止损/warm-up/风险提示/下钻全部保留（UI 零回归）

### 决策 D6: 检测器零修改

- `ReboundDetector.evaluate` 是纯函数且为 live/backtest 单一真源（DETECT-04 / D-01）
- 扫描器只调用 `evaluate`，不修改其逻辑；扫描结果与精跟结果逻辑完全一致
